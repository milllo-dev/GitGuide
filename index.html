Git이란 무엇인가?
버전 관리 시스템의 개념과 Git이 필요한 이유

코드를 작성하다 보면 이런 상황을 마주하게 됩니다. "어제 잘 되던 기능이 갑자기 망가졌다. 어떻게 되돌리지?" 또는 "팀원이 같은 파일을 수정했는데 누구 코드를 써야 하지?" Git은 바로 이런 문제를 해결하기 위해 만들어진 버전 관리 시스템(VCS, Version Control System)입니다.

💡
게임 세이브 포인트처럼 생각하세요

RPG 게임에서 중요한 분기점마다 세이브를 해두듯이, Git은 코드의 변경 사항을 단계별로 저장합니다. 언제든지 원하는 시점으로 되돌아갈 수 있고, 여러 경로(브랜치)를 동시에 탐험할 수 있습니다.

Git이 해주는 것

  • 변경 이력 추적 — 누가, 언제, 왜 코드를 수정했는지 기록합니다.
  • 이전 버전 복원 — 실수한 코드를 특정 시점으로 되돌릴 수 있습니다.
  • 병렬 작업 — 여러 기능을 동시에 독립적으로 개발할 수 있습니다(브랜치).
  • 협업 — 여러 사람이 같은 프로젝트에서 충돌 없이 작업할 수 있습니다.

Git vs GitHub — 뭐가 다른가요?

많은 분들이 Git과 GitHub를 혼동합니다. 핵심 차이를 정리하면 다음과 같습니다.

구분설명비유
Git 내 컴퓨터에서 실행되는 버전 관리 도구 (소프트웨어) 마이크로소프트 워드 (프로그램 자체)
GitHub Git 저장소를 인터넷에 올려두고 협업할 수 있는 플랫폼 (서비스) 구글 드라이브 (문서를 올려두는 클라우드)
ℹ️
GitHub 외에도 유사한 플랫폼이 있습니다

GitLab, Bitbucket 등도 동일한 Git 기반의 협업 플랫폼입니다. 이 가이드에서는 가장 많이 쓰이는 GitHub를 기준으로 설명합니다.

Git 설치하기
Windows와 macOS 환경에서의 설치 방법

Git을 사용하려면 먼저 컴퓨터에 설치해야 합니다. 운영체제에 맞는 탭을 선택해서 진행하세요.

1
Git for Windows 다운로드
git-scm.com/download/win에 접속하면 자동으로 최신 버전 다운로드가 시작됩니다. 64-bit Git for Windows Setup을 선택하세요.
2
설치 프로그램 실행
다운로드된 .exe 파일을 실행하세요. 대부분의 옵션은 기본값으로 진행해도 됩니다. "Use Git from the Windows Command Prompt" 옵션이 선택되어 있는지 확인하세요.
3
Git Bash 확인
설치 후 시작 메뉴에서 Git Bash를 열어보세요. Git Bash는 Windows에서 Unix 방식의 Git 명령어를 사용할 수 있게 해주는 터미널입니다.
4
설치 확인
Git Bash에서 아래 명령어를 입력해 버전을 확인하세요.
bash 
git --version
# 출력 예시: git version 2.44.0.windows.1
💡
Windows Terminal도 함께 설치하는 것을 추천합니다

Microsoft Store에서 Windows Terminal을 설치하면 Git Bash, PowerShell, CMD를 하나의 앱에서 편리하게 사용할 수 있습니다.

macOS에서는 두 가지 방법으로 설치할 수 있습니다.

🍺 방법 1: Homebrew로 설치 추천 ▼

Homebrew는 macOS용 패키지 관리자입니다. 없다면 먼저 설치하세요.

bash 
# Homebrew 설치 (이미 있다면 건너뜀)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# Git 설치
brew install git

# 설치 확인
git --version
🛠️ 방법 2: Xcode Command Line Tools ▼

Homebrew 없이 Apple에서 제공하는 개발 도구 패키지를 통해 설치할 수 있습니다.

bash 
# Xcode Command Line Tools 설치
xcode-select --install

# 팝업 창에서 '설치' 클릭 후 완료를 기다림
# 설치 확인
git --version

터미널은 Launchpad → 기타 → 터미널 또는 Spotlight(⌘ + Space)에서 "terminal"을 검색해 실행하세요.

초기 설정 (필수)

Git을 처음 설치했다면 반드시 이름과 이메일을 설정해야 합니다. 이 정보는 커밋(저장) 기록에 남는 작성자 정보입니다.

bash 
# 이름 설정 (따옴표 안에 본인 이름 입력)
git config --global user.name "Hong Gildong"

# 이메일 설정 (GitHub에 가입할 이메일 권장)
git config --global user.email "hong@example.com"

# 설정 확인
git config --list
⚠️
--global 플래그의 의미

--global을 붙이면 이 컴퓨터의 모든 Git 프로젝트에 적용됩니다. 특정 프로젝트에만 다른 설정을 쓰고 싶다면 해당 폴더 안에서 --global 없이 명령어를 실행하세요.

✅ 설치 체크리스트

기본 커맨드
Git을 사용할 때 가장 많이 쓰이는 핵심 명령어들

Git은 터미널(명령줄)에서 명령어를 입력해서 사용합니다. 처음에는 낯설게 느껴지지만, 몇 가지 핵심 명령어만 익히면 대부분의 작업을 처리할 수 있습니다.

Git의 세 가지 영역

Git 명령어를 이해하려면 먼저 Git이 파일을 어떻게 관리하는지 알아야 합니다. Git은 세 가지 영역을 구분해서 파일을 추적합니다.

파일 상태 흐름도
📝
Working Directory
실제 작업하는 폴더
파일을 수정하는 곳
→
git add
📦
Staging Area
커밋할 파일을
선택하는 대기 공간
→
git commit
🗃️
Repository
커밋이 영구 저장되는
Git 저장소
💡
Staging Area가 왜 필요한가요?

파일을 수정할 때 모든 변경사항을 한꺼번에 커밋하지 않아도 됩니다. "이 파일만 오늘 커밋하고 나머지는 내일"처럼, 커밋할 파일을 선별하는 바구니 역할을 Staging Area가 합니다.

핵심 명령어 사전

git init
새 Git 저장소를 초기화합니다
📖 정의
현재 폴더를 Git이 추적하는 저장소로 만듭니다.
🎯 의도
새 프로젝트를 시작할 때 Git 버전 관리를 적용합니다.
✅ 결과
폴더 안에 .git 숨김 폴더가 생성됩니다.
bash
git init
# 출력: Initialized empty Git repository in /your/path/.git/
git status
현재 저장소의 상태를 확인합니다
📖 정의
어떤 파일이 변경되었는지, Staging Area에 무엇이 있는지 보여줍니다.
🎯 의도
지금 내 작업 상태를 파악하기 위해 가장 자주 사용하는 명령어입니다.
✅ 결과
추적 중인 파일, 수정된 파일, Staging된 파일 목록이 출력됩니다.
bash
git status
# 출력 예시:
# Changes not staged for commit:
#   modified:   index.html
# Untracked files:
#   new-file.js
git add
파일을 Staging Area에 추가합니다
📖 정의
변경된 파일을 다음 커밋에 포함시키기 위해 Staging Area에 올립니다.
🎯 의도
커밋할 파일을 선택합니다. "이 파일의 변경사항을 저장하겠다"는 선언입니다.
✅ 결과
해당 파일이 staged 상태로 바뀝니다. git status에서 초록색으로 표시됩니다.
bash
# 특정 파일만 추가
git add index.html

# 여러 파일 추가
git add index.html style.css

# 현재 폴더의 모든 변경사항 추가 (주의해서 사용)
git add .
⚠️
git add .을 무분별하게 쓰지 마세요

git add .는 모든 파일을 한꺼번에 추가합니다. API 키, 비밀번호가 담긴 설정 파일이나 불필요한 파일이 포함될 수 있습니다. .gitignore 파일을 설정하거나, 가능하면 파일을 명시적으로 지정하는 습관을 들이세요.

git commit
Staged 파일들을 저장소에 기록합니다
📖 정의
Staging Area의 변경사항을 저장소에 영구 기록합니다. "세이브 포인트"를 만드는 것입니다.
🎯 의도
작업 단위를 명확히 구분해서 저장합니다. 메시지를 통해 무엇을 했는지 설명합니다.
✅ 결과
새 커밋이 생성됩니다. 고유한 해시(ID)가 부여되며 git log로 확인할 수 있습니다.
bash
# -m 플래그로 커밋 메시지 작성
git commit -m "로그인 페이지 UI 추가"

# 출력 예시:
# [main a3b8c21] 로그인 페이지 UI 추가
# 2 files changed, 45 insertions(+)
💡
좋은 커밋 메시지 작성법

커밋 메시지는 "무엇을 했는가"보다 "왜 했는가"를 담는 것이 좋습니다. 예시: ✅ "사용자 요청으로 검색 필터 기능 추가" ❌ "코드 수정"

git log
커밋 히스토리를 조회합니다
📖 정의
지금까지 만든 커밋들의 목록과 정보를 보여줍니다.
🎯 의도
과거 작업 이력을 확인하거나 특정 커밋을 찾을 때 사용합니다.
✅ 결과
커밋 해시, 작성자, 날짜, 메시지가 최신 순으로 출력됩니다.
bash
git log

# 한 줄로 간결하게 보기
git log --oneline

# 출력 예시 (--oneline):
# a3b8c21 로그인 페이지 UI 추가
# f9d2e10 프로젝트 초기 설정
# 5a1c4b8 README 작성
git branch
브랜치를 조회하거나 생성합니다
📖 정의
브랜치는 독립적인 작업 공간입니다. 메인 코드에 영향 없이 새 기능을 개발할 수 있습니다.
🎯 의도
새 기능 개발, 버그 수정 등을 독립 공간에서 안전하게 작업합니다.
✅ 결과
브랜치 이름만 적으면 현재 커밋에서 새 브랜치가 만들어집니다.
bash
# 브랜치 목록 보기 (* 표시가 현재 브랜치)
git branch

# 새 브랜치 만들기
git branch feature/login

# 브랜치 삭제 (merge 완료 후)
git branch -d feature/login
git switch  / git checkout
다른 브랜치로 이동합니다
📖 정의
현재 작업 중인 브랜치를 바꿉니다. git switch는 최신 방식, git checkout은 구버전 방식입니다.
🎯 의도
다른 브랜치로 이동해서 해당 브랜치의 코드 상태로 전환합니다.
✅ 결과
HEAD(현재 위치)가 해당 브랜치로 이동하고, 파일이 그 브랜치의 상태로 바뀝니다.
bash
# feature/login 브랜치로 이동 (최신 방식)
git switch feature/login

# 브랜치 생성과 동시에 이동
git switch -c feature/signup

# 구버전 방식 (동일한 결과)
git checkout feature/login
git checkout -b feature/signup
🛠️ 실습 1: 첫 번째 커밋 만들기
새 폴더를 만들고 Git 저장소를 초기화한 뒤, 파일을 추가하고 첫 커밋을 만들어보세요.
  1. 터미널에서 mkdir my-project && cd my-project로 새 폴더를 만들고 이동
  2. git init으로 저장소 초기화
  3. echo "Hello Git" > README.md로 파일 생성
  4. git add README.md로 Staging
  5. git commit -m "첫 번째 커밋"으로 커밋 생성
  6. git log --oneline으로 확인

각 단계 실행 후 git status를 입력해보세요. 파일 상태가 어떻게 변하는지 확인하면 이해가 빠릅니다. git add 전후, git commit 전후로 각각 실행해보세요.

브랜치 & Pull Request
실제 팀 협업에서 사용하는 브랜치 전략과 PR 워크플로우

Git이 강력한 이유 중 하나는 브랜치(Branch)입니다. 브랜치를 사용하면 메인 코드를 건드리지 않고, 독립된 공간에서 자유롭게 작업할 수 있습니다. 작업이 완성되면 PR(Pull Request)을 통해 코드 리뷰를 받고 메인 코드와 합칩니다.

🌿
브랜치는 "평행 우주"입니다

브랜치를 만드는 순간, 메인 코드와 독립된 복사본이 생깁니다. 이 복사본에서 마음껏 수정하고 실험할 수 있습니다. 잘못되어도 메인 코드에 영향이 없고, 잘 되면 merge해서 합치면 됩니다.

브랜치 다이어그램

아래 다이어그램은 main 브랜치에서 feature/login 브랜치를 분기해서 작업하고, PR을 통해 다시 합치는 흐름을 보여줍니다.

브랜치 분기 및 머지 흐름
main
HEAD
feature
main 커밋 feature 커밋 merge 커밋

단계별 협업 워크플로우

1
새 브랜치 만들기
작업하기 전에 항상 새 브랜치를 만듭니다. 브랜치 이름은 작업 내용을 설명하도록 짓습니다.
bash
# main에서 새 브랜치 생성 후 이동
git switch -c feature/login
2
작업 후 커밋
파일을 수정하고 git add + git commit으로 변경사항을 기록합니다. 작은 단위로 여러 번 커밋하는 것이 좋습니다.
bash
git add login.html login.css
git commit -m "로그인 폼 HTML/CSS 추가"

# 추가 작업 후 또 커밋
git add login.js
git commit -m "로그인 폼 유효성 검사 로직 추가"
3
리모트에 푸시
내 브랜치를 GitHub(리모트 저장소)에 올립니다. 처음 푸시할 때는 -u origin을 붙여야 합니다.
bash
# 처음 푸시할 때 (-u는 "upstream" 설정)
git push -u origin feature/login

# 이후 추가 푸시할 때
git push
4
GitHub에서 Pull Request 생성
GitHub 레포지토리 페이지에 접속하면 방금 푸시한 브랜치를 감지해 "Compare & pull request" 버튼이 나타납니다. 클릭해서 PR을 생성하세요.
ℹ️
Pull Request란 무엇인가요?

PR(Pull Request)은 "내 브랜치의 변경사항을 메인 브랜치에 당겨서 합쳐달라(Pull + Merge)는 요청"입니다. 팀원들이 코드를 검토(Code Review)하고, 문제가 없으면 Merge 버튼을 눌러 합칩니다.

5
코드 리뷰 및 Merge
팀원들이 코드를 확인하고 승인(Approve)하면, GitHub에서 "Merge pull request" 버튼을 눌러 main 브랜치에 합칩니다.
6
로컬 main 업데이트
GitHub에서 merge가 완료됐으면, 내 로컬 컴퓨터의 main 브랜치도 최신 상태로 업데이트합니다.
bash
# main 브랜치로 돌아가기
git switch main

# 리모트의 최신 변경사항 가져오기
git pull

# 작업 완료한 브랜치 삭제 (선택사항)
git branch -d feature/login

브랜치 이름 컨벤션

팀마다 다르지만, 아래와 같이 접두사를 붙이는 방식이 널리 사용됩니다.

접두사용도예시
feature/새 기능 개발feature/user-login, feature/dark-mode
fix/버그 수정fix/login-crash, fix/typo-header
docs/문서 수정docs/update-readme
refactor/코드 구조 개선 (기능 변경 없음)refactor/auth-module
hotfix/긴급 버그 수정hotfix/payment-error
⚠️
main 브랜치에서 직접 작업하지 마세요

main(또는 master) 브랜치는 배포 가능한 안정적인 코드를 유지하는 공간입니다. 작업은 항상 별도 브랜치에서 하고 PR을 통해 합치세요. 혼자 작업하더라도 이 습관을 들이면 나중에 협업 시 자연스럽게 적용됩니다.

🛠️ 실습 2: 브랜치 만들고 merge하기
앞서 만든 my-project 저장소에서 브랜치를 만들어 파일을 수정한 뒤, main에 merge 해보세요.
  1. git switch -c feature/add-info로 새 브랜치 생성
  2. echo "작성자: 홍길동" >> README.md로 파일 수정
  3. git add README.md && git commit -m "README에 작성자 정보 추가"
  4. git switch main으로 main 복귀
  5. git merge feature/add-info로 merge
  6. git log --oneline으로 커밋 이력 확인

git merge는 현재 브랜치에 다른 브랜치의 변경사항을 가져오는 명령어입니다. main에서 실행하면 feature 브랜치의 커밋이 main에 합쳐집니다. merge 후 git log --oneline --graph를 실행하면 브랜치 그래프를 볼 수 있습니다.

✅ 브랜치 & PR 체크리스트
5
로컬 & 리모트
내 컴퓨터(로컬)와 GitHub(리모트)의 관계

Git을 혼자 쓸 때는 내 컴퓨터에서만 작업하지만, 협업을 하거나 코드를 백업하려면 인터넷에 있는 원격 저장소(리모트)와 연결해야 합니다. 가장 널리 쓰이는 리모트 서비스가 GitHub입니다.

로컬과 리모트의 관계
💻
로컬 (Local)
내 컴퓨터
실제로 작업하는 곳
git push →
← git pull
☁️
리모트 (Remote)
GitHub 서버
코드를 공유하고 백업하는 곳

핵심 명령어

git clone
리모트 저장소를 로컬로 복사합니다
📖 정의
GitHub 등 리모트 저장소의 전체 내용을 내 컴퓨터로 다운로드합니다.
🎯 의도
남의 프로젝트나 기존 팀 프로젝트에 처음 참여할 때 사용합니다.
✅ 결과
새 폴더가 생기고 리모트의 모든 코드와 커밋 이력이 복사됩니다.
bash
git clone https://github.com/username/repository-name.git

# 폴더 이름을 직접 지정하고 싶을 때
git clone https://github.com/username/repository-name.git my-folder
git remote add
리모트 저장소를 연결합니다
📖 정의
로컬 저장소에 리모트 저장소 주소를 등록합니다.
🎯 의도
git init으로 만든 로컬 저장소를 GitHub의 새 레포지토리와 연결할 때 사용합니다.
✅ 결과
origin이라는 이름으로 리모트 주소가 저장됩니다. 이후 git push origin ...처럼 사용합니다.
bash
git remote add origin https://github.com/username/repository-name.git

# 현재 연결된 리모트 확인
git remote -v
git push
로컬 커밋을 리모트로 업로드합니다
📖 정의
로컬에서 만든 커밋들을 리모트 저장소에 올립니다.
🎯 의도
내 작업을 백업하거나 팀원들과 공유할 때 사용합니다.
✅ 결과
GitHub에서 내 커밋들을 볼 수 있게 됩니다.
bash
# 현재 브랜치를 origin 리모트에 푸시 (최초 1회)
git push -u origin main

# 이후 추가 푸시
git push
git pull
리모트 변경사항을 로컬로 가져옵니다
📖 정의
리모트의 최신 커밋을 로컬로 다운로드하고 현재 브랜치에 merge합니다.
🎯 의도
팀원이 push한 새 코드를 내 로컬에 반영할 때 사용합니다.
✅ 결과
로컬 브랜치가 리모트의 최신 상태와 동기화됩니다.
bash
# 현재 브랜치의 리모트 변경사항 가져오기
git pull

# 특정 리모트/브랜치 지정
git pull origin main
💡
"origin"은 관례적인 이름입니다

origin은 리모트 저장소의 별명(alias)일 뿐입니다. git remote add github https://...처럼 다른 이름도 가능합니다. 하지만 모든 팀에서 origin을 기본 리모트 이름으로 사용하므로, 이 관례를 따르는 것이 좋습니다.

🛠️ 실습 3: GitHub에 푸시하기
GitHub에 새 레포지토리를 만들고 로컬 프로젝트를 연결해서 push 해보세요.
  1. GitHub에 로그인 후 New repository 버튼으로 새 레포 생성 (README 파일 없이)
  2. 로컬 프로젝트에서 git remote add origin <레포 URL>
  3. git push -u origin main으로 푸시
  4. GitHub 페이지를 새로고침해서 코드가 올라갔는지 확인

GitHub에서 새 레포를 만들면 페이지에 git remote add origin ... 명령어가 적혀 있습니다. 그것을 그대로 복사해서 실행하면 됩니다. git push -u origin main에서 -u는 이후 git push만 입력해도 같은 곳에 push되도록 기본 설정을 저장하는 옵션입니다.
